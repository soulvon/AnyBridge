## 1. 审计核心发现：handlers/chat.js 平行重试（T1 §5.5 未审计项补齐）

`attemptNext()` 是一套与 `execute()` **语义平行但细节分歧**的重试实现。默认参数相同
（maxRetries=5 / base=600 / cap=8000 / total=60s），分歧共 7 处：

| # | 维度 | execute()（local-proxy.js） | chat.js | 定性 |
|---|---|---|---|---|
| 1 | 可重试状态码 | 408/425/429/500-504/**520-524**/529（L74） | 408/425/429/500-504/529（**缺 520-524**，L93） | 分歧：Cloudflare 瞬断码两条链路待遇不同 |
| 2 | Retry-After | **完全不读**（T1 实测 31ms） | **支持**：`max(jitter, clamp(RA,0,capMs))`，秒数与 HTTP-date 双解析（L100-109,132-135） | 分歧：本轮决策三据此翻转 |
| 3 | 重试闸门 | 首字节前（响应头阶段判定） | 追加 `!res.headersSent`（L1061，下游头已发即不重试） | chat.js 更保守（合理，不效仿） |
| 4 | 客户端断开 | 无显式保护 | `res.on('close')` 清 retryTimer + 销毁在途请求（L932-945） | chat.js 更好（记录，本轮不动） |
| 5 | 统计 | `recordRetry` 有（retries 指标） | **无 recordRetry**（retries 恒 0，L26 只导入 recordRequest/recordUsage/recordError/recordLatency） | 分歧：决策四记录 |
| 6 | 在途请求控制 | 无 AbortSignal 透传 | `bindActiveReq` + 断开销毁 | 同 4 |
| 7 | 另有一次性补偿重试 | 无 | prompt-cache 被拒移除重试一次（L1396-1411） | 非 R11 范畴，正常设计 |

**处置**：T5 严格只动 `execute()`（02_tasks T5 边界），chat.js 三处分歧（1/2/5）记录在案，
**建议下一轮单列「双链路重试语义统一」任务**（对齐 520-524 一行 + retries 指标接入 + 溢出 clamp 同步），
不在本轮混入无验收覆盖的改动。

## 2. 决策一：maxRetries 默认值——**维持 5，不下调**

### 选择
`maxRetries` 默认维持 5（每目标最多 6 次请求）。T5 对默认值**零改动**。

### 理由
1. **存量配置已固化，改默认对存量用户无效**（本轮新实证）：
   - `EnhancementConfig.retryMaxRetries` 的 serde 无 `skip_serializing_if`（model_map.rs L173-174）→ **写盘必带该字段**；
   - UI `50-model-map.js` L11-16 还有第四处默认值副本 `DEFAULT_PROXY_ENHANCEMENT`，载入时 normalize 必写数值（L136-141）；
   - 本机存量 `model-map.json` 实测显式 `"retryMaxRetries": 5`（AppData 实证）。
   - ⇒ JS/Rust 的默认值形同虚设，改默认**必须清洗用户配置文件才生效**——动用户存量配置的风险与收益不成比例。
2. **默认参数下时间代价可控**（模拟实证，§3）：预算 60s 下 5 次重试的 full-jitter 退避期望 ~8.5s（最坏 ~17s），预算根本不紧、溢出率 0%。用户等待由每目标 60s 预算封顶。
3. **429 主场景由决策三改善**：限流时的无效快速重试（31ms 就重发）将被 Retry-After 拉开间隔，减少对已限流渠道的请求放大——这比下调次数更对症。
4. **放大最坏值（18 次）是「全目标持续故障」场景**：该场景本就以快速失败告终，损失是上游压力而非用户延迟；若未来实测成为问题，优先动「全局预算」而非次数（见决策二边界记录）。
5. **用户已有配置出口**：增强设置页「最大重试次数」可调 0-∞（UI L1852-1856），重度用户可自行下调。

### 影响面
零代码改动。**技术债记录**：`maxRetries=5` 存在 **5 处副本**（local-proxy.js L1063 / model_map.rs L41-43 /
chat.js L73 `BYOK_RETRY_MAX` / 50-model-map.js L13 / model-map.json 存量值），建议未来配置集中化时一并收敛。

## 3. 决策二：总墙钟预算——**粒度维持每目标 60s + 修 sleep 溢出（clamp，一行级）**

### 选择
1. 预算粒度**维持每目标**（`started` 每目标重置，现状语义不变），**不引入跨目标全局预算**。
2. 修正 T1 §5.3 溢出：`delay = min(delay, max(0, totalMs - elapsed))`（clamp 到剩余预算），
   建议收敛在 `retryDelay()` 单函数内实现（5 个判定点共用，传 elapsed）。

### 理由
1. **溢出定性被模拟修正**（`tmp/t6-budget-sim.mjs`，2 万次/组蒙特卡洛）：

```
=== T6 决策二：sleep 溢出模拟（full jitter, base=600, cap=8000）===
[现状默认 maxRetries=5, 预算60s, 失败请求0.5s] sleep 后超预算率=0.0%
[现状默认 maxRetries=5, 预算60s, 失败请求2s  ] sleep 后超预算率=0.0%
[收紧场景 maxRetries=5, 预算10s, 失败请求2s  ] 现状超预算率=65.9% 最坏超时=7907ms → clamp 后 0%（clamp 触发 32102 次）
[收紧场景 maxRetries=3, 预算10s, 失败请求2s  ] 现状超预算率=0.0%
```

   即：**默认 60s 预算下溢出率 0%**（T1 K 组 1917>1000ms 是收紧到 1s 的构造场景）；
   溢出真实存在但只在收紧配置触发。修复价值 = 让「预算」承诺变真，成本一行，收益确定性高 → 修。
2. **不引入全局预算**（避免过度设计）：多目标叠加最坏 3×60s=180s 仅发生在「所有目标持续故障且各打满预算」的极端场景，用户已有客户端超时兜底；全局预算会改变 failover 语义（后面的目标被前面吃掉预算）且最优值随目标数变化，暂无实测案例支撑其必要性。**边界记录**：180s 最坏等待为已知现状，若未来有真实案例再议。

### 影响面（T5 落地）
`local-proxy.js` `retryDelay()`（或 5 个判定点传参）+ 行为测试：收紧预算（如 1s）下
「sleep 排程结束时 elapsed ≤ totalMs」恒成立。chat.js 同款溢出（retryTimer setTimeout 排程后 elapsed 不再查）
列入 §1 统一任务，本轮不动。

## 4. 决策三：Retry-After——**v1 支持（对齐 chat.js 既有模式）**

### 选择
`execute()` 补 `Retry-After` 支持，**照抄 chat.js 已验证模式**：
`retryDelay = max(fullJitter, clamp(Retry-After, 0, capMs))`；解析支持秒数与 HTTP-date 双格式（chat.js L100-109 同款）。

### 理由
1. **不是发明，是对齐**：Windsurf 链路（chat.js）已用该模式实战。若 execute() 继续「不读」，
   同一上游 429+Retry-After:5 时本地代理链路 31ms 就重发（T1 实测）、必再吃 429 白烧重试额度，
   而 Windsurf 链路等 5s——同产品两链路行为分叉扩大。
2. **对症 R11 风险**：限流是最常见的可重试场景之一；尊重 RA（clamp 到 8s cap）让重试落在
   「更可能恢复」的时点，减少无效放大——这正是决策一维持 5 次的配套补偿。
3. **与预算天然兼容**：clamp 到 capMs(8s) ⇒ 单次等待不会拖爆 60s 预算（区别于尊重原始 RA 5-60s+）。
4. 改动面可控：`retryDelay` 加可选 meta 参数 + 5 个判定点传上游响应头（catch 网络分支传 null），
   与决策二的 clamp 落在同一次改动里。

### 影响面（T5 落地）
`local-proxy.js` `retryDelay` 签名 + 5 判定点实参 + 新增 RA 解析函数（可从 chat.js 提取共享或复制同款）+
行为测试：429 + `Retry-After: 3` 实测单次重试等待 ≥ 3s 且 ≤ cap；`Retry-After: 120` 被钳到 8s。
**文档写明**：尊重范围 = clamp 至 capMs；HTTP-date 按 `date - now` 计算后同样钳制。

## 5. 决策四：统计口径——**维持现状三分量 + 新增 upstream_attempts**

### 选择
| 指标 | 语义 | 现状 | 动作 |
|---|---|---|---|
| `requests` | 客户端请求数（每目标 +1，**不含重试**） | 已是此口径（T1 §4.4：4 次上游请求 Δrequests=1） | 不动 |
| `retries` | 重试触发次数（全局累计，`lastRetryReason` 记末次原因） | 已是此口径 | 不动 |
| `errors` | 最终失败（每请求至多 1） | 已是此口径 | 不动 |
| `upstream_attempts` | 上游实际收到的请求总数 | **不存在** | **T5 新增**（独立累计，= requests + retries 的自累计字段，供 R16 按模型/供应商拆分时数据完备） |

### 理由
1. R15 验收口径「连续 3 次请求 requests 增加 3」与现状一致，**不需要改既有字段**（改口径会破坏既有统计连续性与已验收的 R15）。
2. R11 的账面问题（「统计 1 次、实发 4 次」对不上）用 `upstream_attempts` 补全即可对账：attempts = requests + retries。
3. chat.js 链路无 `recordRetry`（§1 分歧 5）→ 该链路 retries 恒 0、attempts=requests。本轮不动（无验收覆盖），
   分歧已在 §1 统一任务记录。

### 影响面（T5 落地）
`sidecar/stats.js` 新增 `upstream_attempts` 累计字段；`recordRetry` 内同步 +1；
`get_stats` 返回体带出；R11 验收「日志有且仅有 1 次重试记录」另需把 recordRetry 信息接到前端日志（T1 §4.3，T5 实现项）。
