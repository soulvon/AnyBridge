## 需求（可测试）

只写能验证的需求，不写愿景。

1. 目标用户/场景：在供应商编辑器里配置供应商的用户；在代理链路发请求时遇到瞬时失败的用户。
2. 输入：供应商地址 / 密钥 / 模型；代理转发经过的 HTTP 请求。
3. 输出：①测试结论持续显示在编辑器内（R19） ②拉取模型后显示数量或失败原因（R22） ③瞬时失败自动重试一次（R11）。
4. 边界条件：①从未测试过的编辑器不显示结果区 ②拉取失败也要有反馈，不能静默 ③流式请求不重试。

## 验收标准（EARS 风格）

用“当 / 如果 / 那么”写，每条都要能对应一个命令或测试。

- WHEN 在编辑器点「测试连接」且密钥错误 THEN 结果区常驻显示失败原因，验收：人工步骤（测试后不自动消失）
- WHEN 再次点「测试连接」 THEN 结果区内容被新结论替换，验收：人工步骤
- WHEN 离开编辑器再返回 THEN 不显示上一次结论，验收：人工步骤
- WHEN 点「拉取模型」且端点可用 THEN 显示「获取到 N 个模型」且与面板条目数一致，验收：人工步骤
- IF 拉取失败 THEN 显示具体原因而不是静默，验收：人工步骤
- WHEN 断网瞬间发请求且网络恢复 THEN 自动重试后成功，验收：日志中恰好一次重试记录
- IF 错误类型属于 T1 结论中「不可重试」 THEN 不产生重试，验收：日志无重试记录
- WHEN 正常请求 THEN 不产生额外请求，验收：请求计数与重试数一致

## 失败模式 / 风险

提前列出可能出错的地方，后面 AI 实现时优先防这些。

- 风险：重试放大请求量（瞬时失败被重复发送）。
- 风险：结果区占用编辑器空间（空态必须不占位）。
- 失败模式：把「拉取成功但 0 个模型」误显示为成功。
- 失败模式：重试判定过宽，对 4xx 也重试。
- 已知道具/依赖：`loadingHtml`（加载态规范）、`proxy.rs`（无 retry 实现）、`fetchModelsForEditor`（无结果反馈）。
