### 1.1 判定函数的唯一定义

### 1.3 「连接断开」怎么判

连接层故障**不产生 HTTP 状态码**，走 `catch` 分支（L2179-2185）：

```2181:2182:sidecar/local-proxy.js

`ECONNRESET`（对端重置/断网瞬间）、`ETIMEDOUT`（含上游挂起被 watchdog 掐断，
见 `lib/upstream-watchdog.js` L80-82 `err.code = 'ETIMEDOUT'`）、`ENOTFOUND`/`EAI_AGAIN`（DNS）、
`ECONNREFUSED`（端口无监听）、`EPIPE`、`EHOSTUNREACH`、`ENETUNREACH`。

实测：

```

> `ECONNREFUSED` 那行「上游请求数=0」是预期的：连接根本没建立，mock 服务端
> 看不到请求；但耗时 61ms（对比不可重试的 14ms）证明确实尝试了 4 次。

### 1.4 三个闸门（决定是否真的重试）

每次 `while(true)` 循环失败后，必须**同时**满足才重试（L2040/2090/2121/2167/2181 同一句式）：

| 闸门 | 代码 | 默认值/来源 |
|---|---|---|
| ① 开关 | `policy.enabled` | `enhancement.retry !== false`，默认开（L1063）；路由级 `route.enhancement.retry === false` 可单独关（L1923） |
| ② 次数 | `retryCount < policy.maxRetries` | 默认 5（L1063），只能由 **model-map.json 全局** 配 |
| ③ 墙钟 | `Date.now() - started < policy.totalMs` | 默认 60s（L1063），`started` 每个目标重置（L2009） |

外加：客户端主动 abort（`AbortError`）不会重试——它不匹配任何集合。

## 2. 结论二：最多重试几次

### 2.1 单层：每目标 `maxRetries` 次重试，即最多 `maxRetries + 1` 次请求

```1062:1067:sidecar/local-proxy.js
function retryPolicy(enhancement = {}) {
  return { enabled: enhancement.retry !== false, maxRetries: positiveInt(enhancement.retryMaxRetries, 5, 0), baseMs: positiveInt(enhancement.retryBaseMs, 600, 1), capMs: positiveInt(enhancement.retryCapMs, 8000, 1), totalMs: positiveInt(enhancement.retryTotalSeconds, 60, 1) * 1000 };
}
function sleep(ms) { return new Promise(resolve => setTimeout(resolve, ms)); }
function retryDelay(attempt, policy) { return Math.round(Math.random() * Math.min(policy.capMs, policy.baseMs * Math.pow(2, Math.max(0, attempt - 1)))); }
```

**默认 maxRetries = 5**（文件 L1063；亦见 `src-tauri/src/commands/model_map.rs` L41-54 的
`default_retry_max_retries` 等）。

实测：
- 显式 `retryMaxRetries: 3` → 上游 4 次
- 无 `model-map.json`（走默认）→ 上游 **6 次**，耗时 9886ms / 11562ms（full jitter 波动）

```
=== E. 默认策略（无 model-map.json）===
HTTP 503  无 model-map.json（默认 maxRetries） | 上游请求数= 6 | 耗时=11562ms | throw: upstream HTTP 503
```

### 2.2 放大：总请求数 = 目标数 × (maxRetries + 1)

```2002:2010:sidecar/local-proxy.js

`retryCount = 0` 在**目标循环内部**（L2010 ⊂ L2002），所以每个目标独立拿满重试额度。

实测（maxRetries=2 → 每目标 3 次）：

```

targets=2                            | 上游请求数= 6 | 耗时=   78ms

**最坏情况：默认 5 次重试 + 3 个上游目标 = 一次用户请求打出最多 18 次上游请求。**
这是 R11 风险栏「放大请求量」的量化结果，T5 定次数时必须考虑。

### 2.3 退避与预算

- 退避：**full jitter**，`rand() × min(8000, 600 × 2^(attempt-1))`（L1067）
- 预算：`totalMs` 默认 60s（L1063），超时即停止重试。实测 `retryTotalSeconds=1 / maxRetries=5` 时
  只打了 5 次（而非 6 次）就被墙钟截断：

```

503 预算 1s 截断                         | 上游请求数= 5 | 耗时= 1917ms
```

### 2.4 已知坑：429 不读 `Retry-After`

`execute()` 的重试**完全不解析** `Retry-After`，429 与 5xx 走同一套指数退避。
只有 `sidecar/retry.js` 里实现了 `Retry-After`（L129-136）——而该文件**没有任何调用方**：

```

  引用 retry.js 的文件数 = 0
  → 结论：retry.js 的 withRetry/httpsRequestAsync 无调用方，属死代码
```

实测（上游返回 `Retry-After: 5`，maxRetries=1 → 共 2 次请求）：

```

```

若尊重 `Retry-After: 5`，耗时应 ≥ 5000ms；实测 31ms → **确认忽略该头**。
（T5 若要补，这是唯一需要新增的判定分支，且不属于 fallback/R9 范畴。）

## 3. 结论三：是否影响流式响应

### 3.1 结论：**不影响**（首字节前的失败照常重试，次数与非流式完全一致）

实测（maxRetries=2 → 期望各 3 次）：

```

HTTP 429  stream=true                | 上游请求数= 3 | 耗时=   45ms
HTTP 429  stream=false               | 上游请求数= 3 | 耗时=   45ms
HTTP 503  stream=true                | 上游请求数= 3 | 耗时=   45ms
HTTP 503  stream=false               | 上游请求数= 3 | 耗时=   45ms
HTTP 520  stream=true                | 上游请求数= 3 | 耗时=   30ms
HTTP 520  stream=false               | 上游请求数= 3 | 耗时=   28ms
```

### 3.2 为什么：重试判定发生在「任何字节转发给客户端」之前

三条真流式分支的写法完全同构——先拿状态码，2xx 才交出响应对象：

```2016:2027:sidecar/local-proxy.js

          const r = await requestUpstreamStream(conn, payload, enhancement);
          recordLatency(r.durationMs); markSuccess(targetKey(target));
          if (r.statusCode >= 200 && r.statusCode < 300) {
            const extraRespHeaders = {};

              for (const h of enhancement.responseHeaders) {
                if (h && h.key) extraRespHeaders[h.key] = h.value;
              }
            }
            return { conn, stream: true, upstreamResponse: r.response, extraHeaders: extraRespHeaders, watchdog: r.watchdog };
          }
```

关键在于 `requestUpstreamStream` 是**在响应头到达时就 resolve**（L1519-1537 的
`settleHeader`），并把 `apiRes` 原样交给调用方。所以：

- 非 2xx → 先 `collectStreamBody(r.response)` 收错误体 → 走 L2040/2090/2121 重试
- 2xx → 才 `return { stream: true, upstreamResponse }`，此时客户端**一个字节都还没收到**

代码注释也明确写了这个契约（L2307-2309）：

```2307:2309:sidecar/local-proxy.js
// 真流式出口：消费上游 SSE（Responses / Anthropic / Chat），逐块转成 Chat SSE 下发。
// 上游形态由 createChatSSEConverter 按 conn 判定；首字节前的失败已在上游请求层重试，
// 这里只管增量转发与收尾（finish + usage + [DONE]）。
```

**推论**：首字节之前的失败（连接断开 / 429 / 5xx）对流式**完全安全**——重发整包请求，
不会有任何内容已被下游消费，不存在重复输出。

OpenAI 流式错误语义一致，是合理的取舍。

## 4. 给 T5 的约束（本轮只记录，不实现）

1. **重试机制已经存在**，`sidecar/local-proxy.js` L2013-2186。T5 不需要再写一套
   `withRetry`，更不要去启用 `sidecar/retry.js`（它是死代码，且没有 `AbortSignal`
   透传与统计挂钩）。
2. **次数**：默认 `maxRetries=5` 且有「目标数 × 6」的放大效应。T5 定次数时须按
   **每目标** 计，并评估多目标场景的最坏放大倍数。
3. **日志可见性**：当前重试只有 `console.warn`（L2042 等）落 sidecar stdout，
   UI 侧看不到。R11 验收要求「日志有且仅有 1 次重试记录」，T5 需把
   `recordRetry` 的信息接到前端日志。
4. **统计口径（关联 R15）**：实测一次用户请求触发 3 次重试后：

```
=== J. 重试是否进入统计（stats.retries / requests）===
503 ×3 重试                            | 上游请求数= 4 | 耗时=   61ms
  Δretries=3  Δrequests=1  Δerrors=1  lastRetryReason=HTTP 503: simulated 503
```

即 **上游实际 4 次请求，但 `requests` 只 +1**（`recordRequest` 在每目标循环内、
重试循环外，L2007）。R15 验收「requests 增加 3」的口径若要含重试，
T5/R15 需先统一，否则会出现「统计 1 次、实发 4 次」的账面对不上。
5. **不做的东西**（严格遵守任务边界）：不做 fallback（R9）、不做跨供应商回退、
   不做流式中途重试。

## 5. 未验证项

1. **真实厂商的 `Retry-After` 语义**：只验证了「代码不读该头」，未验证各厂商
   实际是否下发、下发的单位是秒还是 HTTP-date。
2. **429 的正确退避时长**：当前 429 与 5xx 同一退避曲线。默认 5 次重试打满
   约 17s 上限（600+1200+2400+4800+8000）。对严格限流的渠道，这个力度是否
   合适、是否需要按 `Retry-After` 加权，未做压测验证。
3. **墙钟预算的竞态**：闸门 ③ 用 `Date.now() - started < totalMs`，
   在最后一次重试的 sleep 已经排程后不会被再次打断，可能出现「总耗时 > totalMs」
   的溢出（K 组实测 1917ms > 1000ms）。属既有行为，未评估是否需要在 T5 收紧。
4. **流式中途断流的客户端表现**：只在 Node 侧验证了「错误透传、上游只打 1 次」，
   未验证各 IDE（Cursor / Windsurf / Codex）收到 SSE error 事件后的实际 UI 表现。
5. **`execute()` 之外是否还有第三条转发路径**：已确认 `cursor-proxy.js` 复用
   `execute`（L14 导入），`inference-proxy.js` / `handlers/chat.js` 属 Windsurf 拦截链路，
   本次未逐个审计其内部是否另有重试。
6. **冷却与重试的交互**：`provider-cooldown.js` 只在 `targets.length >= 2` 时生效
   （L121），单目标场景下失败不会进入冷却。多目标冷却时长与重试次数的联合最坏耗时未测。
