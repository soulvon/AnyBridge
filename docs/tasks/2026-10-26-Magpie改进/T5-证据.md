## 验收实测（`node tmp/t5-verify.mjs`，18/18 全绿，全本地 mock）

```
=== 验收① 单目标请求数 = maxRetries+1 ===
  ✅ 单目标 maxRetries=3 → 上游 4 次 — hits=4

=== 验收② 多目标放大（maxRetries=2 → 每目标 3 次）===
  ✅ targets=1 → 上游 3 次   ✅ targets=2 → 上游 6 次   ✅ targets=3 → 上游 9 次

=== 验收③ 墙钟预算溢出修正（totalMs=1s, base=600, cap=8000, maxRetries=5）===
  ✅ 请求跨度 ≤ 预算 1000ms + 150ms 容差 — 实测跨度=1003ms（T1 旧代码同场景实测 1917ms）
  ✅ 预算截断生效（未打满 6 次） — hits=4

=== 验收④ Retry-After（maxRetries=1, base=600, cap=8000）===
  ✅ Retry-After: 3 → 退避 ≈ 3s（取大） — 实测间隔=3011ms
  ✅ Retry-After: 120 → 钳到 cap 8s — 实测间隔=8005ms
  ✅ Retry-After(HTTP-date ≥+2s) → ≥ 2s — 实测间隔=2170ms
  ✅ 无 Retry-After → 纯 jitter ≤ 600ms — 实测间隔=514ms

=== 验收⑤ 流式边界（maxRetries=2 → 3 次）===
  ✅ 流式 503 → 上游 3 次（与非流式一致）   ✅ 非流式 503 → 上游 3 次
  ✅ 流式中途断流 → 上游只打 1 次（不重试）— 下游错误=ECONNRESET

=== 验收⑥ 指标口径（503 ×3 重试，单目标）===
  ✅ Δrequests = 1（客户端口径，不含重试）  ✅ Δretries = 3
  ✅ ΔupstreamAttempts = 4（= requests + retries）
  ✅ snapshot 带 lastRetryReason — HTTP 503: simulated 503
  ✅ recent 含 retry 事件（UI 日志数据源）— provider=Mock
```

判据说明：
- 验收③黑盒判定 = mock 端请求到达跨度 `arrivals[last] - arrivals[0] ≤ totalMs + 150ms 容差`（arrivals[0]≈started；容差覆盖连接/调度开销）。修复前同场景 T1 实测 1917ms，修复后 1003ms，clamp 生效。
- 验收④间隔 = `arrivals[1] - completions[0]`（sleep 精确值 = 下次到达 - 上次响应完成）。探针初版 HTTP-date 断言失败为**探针自身问题**（`toUTCString()` 秒级精度丢毫秒，实测 1377ms 仍 > jitter 上限 600 已证 RA 生效），修正 mock 端 date 向上取整到整秒后通过——实现无缺陷。

## 行为变化说明（对用户的可见差异）

1. 上游返回 `Retry-After` 时（429 常见），重试退避从「纯 jitter ≤ 8s」变为「max(jitter, RA≤8s)」——限流渠道的重试落在更可能恢复的时点，减少无效请求。
2. 收紧 `retryTotalSeconds` 的用户：重试等待不再越过预算墙（默认 60s 预算下本就几乎不触发）。
3. UI 日志面板新增 `warn` 级「<供应商> 上游重试 ×N：<原因>」条目（3s 内可见，来自既有统计轮询）。
4. `stats.json` / `__byok/stats` 新增 `upstreamAttempts` 字段（持久化累计，语义 = requests + retries）。
